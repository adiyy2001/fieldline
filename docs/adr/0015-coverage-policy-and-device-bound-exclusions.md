# 15. Coverage policy and device-bound exclusions

Status: accepted

## Context

The definition of done asks for 90 percent line coverage of the core logic (domain, math, algorithms) and 80 percent for everything else. Code that talks to a GPU device cannot run in jsdom, and a real adapter is only available in a browser. Excluding such files silently would let the number lie.

## Decision

- Vitest enforces line thresholds per directory: `src/core/**` 90 percent, `src/app/**` 80 percent, `src/gpu/**` 80 percent, `src/workers/**` 80 percent.
- Files that need a real `GPUDevice` or a worker global are excluded from the unit coverage run. The exclusion list lives in one module that both the Vitest configuration and the style script import.
- A guard in `pnpm check:style` fails when a file outside the list calls a device API (`createBuffer`, `createComputePipeline`, `createTexture`, `getContext('webgpu')`, `queue.submit`) or when a listed file no longer exists. The list cannot go stale and cannot hide new device code.
- Everything kept out of the unit run is covered by Playwright specs instead: the smoke kernel, the field kernel parity, the marching-cubes pass, the ray marcher and the field line trace. The pure parts of those modules (packing, layouts, table generation, camera math, parameter validation) live in separate files that do count.
- The coverage report is generated by `pnpm test:coverage`, and the README quotes numbers from that run.

## Alternatives

- One global threshold of 80 percent. It would let the physics core fall below the stricter bar.
- Excluding the whole `gpu` directory. It would hide the pure helpers that are easy to test.
- Measuring coverage inside Playwright with V8 coverage. It is possible, but merging reports adds complexity for little gain.

## Consequences

- Device-bound modules stay thin: they create resources and call into pure helpers.
- A new GPU file forces a decision, either a test that can run or an entry in the list with a Playwright spec that covers it.
